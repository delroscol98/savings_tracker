# Savings Tracker Backend Architecture

An overview of how the backend is organized and how the pieces fit together.

## Request flow

```
HTTP request
   │
   ▼
internal/router  (routes + middleware wrapping)
   │   GET /health, POST /api/users, ... (public)
   │   GET /api/goals, ...              (middleware.RequireAuth)
   ▼
middleware
   │   Log         → logs method + path
   │   RequireAuth → validates JWT, injects userId into context
   ▼
handlers (api/users, api/goals, api/health)
   │   decode body → validate → call Queries → map errors to responses
   ▼
internal/database  (sqlc-generated, type-safe SQL)
   ▼
PostgreSQL
```

## Directory layout

```
backend/
├── main.go                    Entrypoint: env loading, config wiring, HTTP server
├── sqlc.yaml                  sqlc config (schema + queries → internal/database)
├── api/                       HTTP layer — one package per domain
│   ├── users/                 Register, login, password reset, email sending
│   ├── goals/                 Goals and deposits
│   └── health/                Liveness/DB-ping check
├── internal/                  Not importable outside this module
│   ├── auth/                  argon2id hashing, JWT, reset tokens, validation
│   ├── database/              sqlc-generated code (do not edit by hand)
│   ├── middleware/            RequireAuth, Log, MetricInc
│   ├── ratelimit/             IP rate limiter + per-account login throttler
│   ├── response/              JSON response helpers
│   └── router/                Route registration
└── sql/
    ├── schema/                goose migrations (numbered)
    └── queries/               sqlc source queries
```

### Layers in detail

**`api/`** — the HTTP layer. Handlers decode the request body, run validation,
call an interface defined in their config, and translate errors into HTTP
responses. They know nothing about the concrete DB implementation.

**`internal/`** — everything that could be reused or that shouldn't leak to the
outside world. `internal/database` is generated by sqlc and is the only package
that touches SQL directly.

**`sql/`** — the source of truth for the database. Migrations are applied with
goose; queries are compiled to Go with sqlc.

## Dependency injection pattern

`main.go` is the composition root. It builds each handler's config struct,
which takes **interfaces** rather than concrete types:

```go
type UsersConfig struct {
    Queries                  Queries        // interface, see api/users/users.go
    Database                 *sql.DB
    PasswordResetRateLimiter *ratelimit.RateLimiter
    LoginRateLimiter         *ratelimit.RateLimiter
    LoginThrottler           *ratelimit.LoginThrottler
    EmailSender              EmailSender    // interface
    JWTSecret                string
    BaseURL                  string
}
```

```go
type GoalsConfig struct {
    Queries Queries
}
```

These structs are passed to `router.NewRouter` and their handler methods are
registered as `http.HandlerFunc`s.

Why this design:

- **Testability** — tests implement the `Queries` interface (see
  `api/goals/mock_db_test.go`, `api/users/mock_db_test.go`) to exercise
  handlers without a database.
- **Explicit dependencies** — every dependency a handler needs is visible in
  its config; there is no hidden global state.
- **Swap-friendly** — e.g. `EmailSender` is satisfied by the real
  `ResendSender` in production and by a mock in tests.

## The sqlc workflow

SQL is the source of truth; generated Go code is a build artifact.

1. **Write a migration** in `sql/schema/NNN_description.sql` (goose Up/Down).
2. **Write a query** in `sql/queries/*.sql`:

   ```sql
   -- name: CreateDeposit :one
   INSERT INTO deposits (id, amount, note, created_at, goal_id, user_id)
   VALUES (gen_random_uuid(), $1, $2, NOW(), $3, $4)
   RETURNING *;
   ```

   The `:one`/`:many`/`:exec` annotations control the generated signature.
3. **Regenerate**:

   ```sh
   sqlc generate
   ```

4. Generated functions land in `internal/database` and are called through the
   config's `Queries` interface.

Computed fields live in SQL too — goal `progress` is a `COALESCE(SUM(...))`
over the deposits join (see `sql/queries/goals.sql`), so the API never has to
recompute it.

## Authentication flow

### Login and JWT issuance

1. `POST /api/login` validates credentials against the argon2id hash.
2. `auth.MakeJWT` signs a token with HS256. Claims: issuer
   `savings-tracker-access`, subject = user ID, issued-at, and expiry
   (`expires_in` seconds, default 3600).
3. The token is returned in the login response.

### Authorization on protected routes

1. `middleware.RequireAuth` extracts the `Authorization: Bearer <token>`
   header via `auth.GetBearerToken`.
2. `auth.ValidateJWT` verifies signature, signing method, expiry, and issuer,
   and returns the user ID.
3. The user ID is stored in the request context with
   `middleware.WithUserId`, and handlers read it with `middleware.GetUserId`.
4. Handlers that touch a resource also verify ownership (e.g.
   `GET /api/goals/{goalId}/deposits` compares the token's user with the
   goal's `user_id`, returning `403` on mismatch). This is defense in depth —
   ownership checks are scoped in the SQL queries too (`WHERE id = $1 AND
   user_id = $2`).

### Password reset

Reset tokens are opaque random hex, stored only as a SHA-256 hash
(`internal/auth/tokens.go`). They expire after 30 minutes and are single-use:
`ConsumePasswordResetToken` marks them consumed in the same transaction that
updates the password. `forgot-password` always returns the same generic
message to avoid leaking whether an email is registered.

## Security measures

- **Password hashing** — argon2id with default params
  (`internal/auth/hash_password.go`).
- **Common passwords** — rejected via a bundled list of the 10k most common
  passwords (`internal/auth/data/`).
- **Rate limiting** — in-memory per-IP limiters: login (10 per 15 min) and
  password resets (5 per 15 min) (`internal/ratelimit/ratelimit.go`).
- **Account lockout** — `LoginThrottler` locks an email after 5 failed logins
  within 15 minutes; the lock clears on success
  (`internal/ratelimit/login_throttler.go`).
- **JWT hardening** — HS256 signature check, issuer pinning, expiry enforced.
- **Input validation** — centralized in `ValidateX` functions per domain
  (`api/users/validate.go`, `api/goals/validate.go`, `internal/auth/validate.go`),
  surfaced to clients as field-level errors.

## Error responses

All responses flow through `internal/response`:

- `RespondWithJSON` — marshals any payload, sets `Content-Type: application/json`.
- `RespondWithError` — `{"error": "..."}` envelope.
- `RespondWithValidationError` — `{"error": "...", "fields": {...}}` envelope
  for field-level validation messages.

Handlers map domain errors to status codes centrally, so clients see a
consistent shape (see `docs/API.md` for per-endpoint codes).

## How to add a new endpoint

End-to-end example for adding a feature:

1. **Schema** — add a goose migration in `sql/schema/`.
2. **Query** — add the SQL to the relevant `sql/queries/*.sql` file.
3. **Generate** — run `sqlc generate`.
4. **Handler** — add the handler method on the domain's config struct, using
   the `Queries` interface.
5. **Validation** — add a `Validate...` function for request body checks.
6. **Route** — register it in `internal/router/router.go`, wrapping with
   `middleware.Log` (and `middleware.RequireAuth` if protected).
7. **Tests** — unit tests with a mocked `Queries` interface, plus an
   integration test under `api/` if it exercises the database.
